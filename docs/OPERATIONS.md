## Backup and recovery rehearsal — not yet tested

There is no evidenced database backup schedule, retention policy, agreed RPO/RTO, or completed restore drill. The private Git repository protects source history only; it is not a backup of PostgreSQL records, Auth identities/MFA, storage, provider configuration, or application secrets. The current local financial database is documented as empty, but do not rely on that assumption when selecting a target. Supabase provider backups and what they cover have not been verified for an operational project. Backup-authenticator self-service is tested; all-factors-lost recovery and data restoration are separate and untested.

Before any rehearsal, the owner must choose the fictional-only scope, a named disposable source and target, retention/access rules, and provisional recovery time/data-loss objectives. Use only `.invalid` identities and synthetic tenant, room, agreement, charge, cash, check, handover, access and audit records. Do not connect to hosted development or production. Never use `db reset`, migration push, restore, cleanup, or test scripts against the preserved local database as a shortcut. Keep dumps outside the repository in a restricted temporary directory; do not print them, commit them, or include credentials in command history or evidence.

Rehearsal sequence:

1. Confirm the Docker Linux engine works and identify the disposable source and a different disposable restore target by their local-only project IDs and ports. Stop if either can resolve to hosted or preserved local data.
2. Create a fictional baseline in the disposable source and record non-sensitive table counts, access roles, migration versions, and expected financial snapshots. Include pending cash and an uncleared check and confirm neither lowers the settled balance.
3. Use the installed Supabase CLI's local dump operation (`npx.cmd supabase db dump --local`) to a restricted temporary file. Separately assess whether Auth users/factors, Storage objects, roles, secrets, edge-function configuration, and provider settings are included; do not assume a database dump covers them. If completeness is unclear, stop and record the gap.
4. Restore only into the separately identified disposable target using PostgreSQL tooling supported by the pinned Supabase CLI/container version. Validate before execution that the destination is the target, not the source. Do not put connection credentials directly in a command, log or report. If no supported restore path is available, do not improvise against another database; ask the owner to approve a maintained rehearsal method.
5. Compare migration state, fictional record counts, exact confirmed balances, allocation/acknowledgment snapshots, pending/check non-settlement, RLS/direct-write denial, MFA/role boundaries, access revocation, invitation history and audit history. Verify the app can authenticate and read only the restored fictional records; never test a real delivery.
6. Record elapsed time, observed data-loss point, missing components, and whether provisional objectives were met. Clean up only the two named disposable projects and restricted temporary dump after evidence review. Preserve redacted evidence and the cleanup result; never claim recovery readiness from a successful dump alone.
7. Separately rehearse owner access recovery with a second enrolled authenticator using fictional accounts. For all-factors-lost recovery, first approve and document the infrastructure owner's identity-verification, provider-admin, audit and re-enrollment process; do not remove MFA or test factor deletion until that procedure is reviewed.

## Owner-approved local cash workflow — not yet exercised

The preserved local cash tables are documented empty and have no designated verifier. Do not create financial records or assign a verifier until the owner completes these checks without sending tenant data into chat:

1. Sign in to the local app as the existing owner and complete MFA. In trusted account management, locate the intended clerk by exact Auth user ID and confirmed email; confirm current active clerk membership and ask the owner to explicitly approve this identity as cash verifier. 2. The owner reviews the actual local tenant, active rental space, responsible tenant, agreed monthly rent, move-in date, and intended first rent month. Confirm whether an agreement or charge already exists and review the displayed balance. Do not treat a missing monthly charge as unpaid rent or invent a rent amount/due-date change. 3. Use only a specific fictional local renter/account and terms explicitly approved for this test. If no approved fictional local fixture exists, do not create a test agreement or payment in the preserved database; use the disposable test runner instead.
4. Record only an owner-approved fictional cash receipt that has already been handed to the authorized collector. Confirm the exact amount/date/collector before saving. Verify the UI shows it as pending and that the settled balance is unchanged.
5. Sign in as the exact owner-approved clerk, complete MFA, verify the pending receipt evidence, and confirm it through the existing confirmation action. Verify the confirmation/acknowledgment is returned by the server and only the confirmed amount changes the balance.
6. Reload the saved account, reopen the issued acknowledgment, and compare its saved amount/date/tenant/location snapshot with the approved test record. Check that pending cash and uncleared checks remain excluded.
7. Record only pass/fail and non-sensitive test identifiers in the status note. Do not include names, email addresses, amounts tied to real renters, credentials, factors, bearer links or provider secrets. Owner approval is required before cleanup or any real financial entry.
